# Quick start

Below is a minimal runnable example. Prerequisites: a running ClickHouse instance
(see [Installation guide](../installation/installation.md#start-a-local-clickhouse-optional-for-testing)),
and the core library + this backend installed.

## Complete example

```python
from typing import Optional, ClassVar
from pydantic import Field
from rhosocial.activerecord.model import ActiveRecord
from rhosocial.activerecord.base.field_proxy import FieldProxy
from rhosocial.activerecord.backend.impl.clickhouse import ClickHouseBackend
from rhosocial.activerecord.backend.impl.clickhouse.config import ClickHouseConnectionConfig

class User(ActiveRecord):
    __table_name__ = "users"
    __primary_key__ = "id"
    c: ClassVar[FieldProxy] = FieldProxy()

    id: Optional[int] = None          # snowflake ID, generated by the backend on save()
    username: str = Field(min_length=3, max_length=50)
    email: str
    age: Optional[int] = None         # -> Nullable(Int32) column

config = ClickHouseConnectionConfig(
    host="localhost", port=8123,
    database="test_db", username="root", password="password",
)

User.configure(config, ClickHouseBackend)

# CREATE — ID generated client-side by the snowflake algorithm and backfilled
user = User(username="alice", email="alice@example.com")
user.save()
print(user.id)            # an Int64 snowflake ID

# READ — ActiveQuery is read-only (DQL)
young = User.query().where(User.c.age < 30).order_by(User.c.username).all()

# UPDATE — instance save() goes through a lightweight UPDATE
user.age = 31
user.save()

# DELETE — instance delete()
user.delete()
```

## Create the table

ClickHouse does not auto-create tables. Before running the above, create a
`MergeTree` table (optional fields use `Nullable(T)`):

```sql
CREATE TABLE IF NOT EXISTS users (
    id        Int64,
    username  String,
    email     String,
    age       Nullable(Int32)
)
ENGINE = MergeTree
ORDER BY (id, username)
SETTINGS enable_block_number_column = 1, enable_block_offset_column = 1;
```

> ⚠️ `SETTINGS enable_block_number_column = 1, enable_block_offset_column = 1`
> is a prerequisite for UPDATE/DELETE — ClickHouse 26.x rejects lightweight
> mutations by default. See [Mutations (UPDATE/DELETE)](../capabilities/mutations.md).
>
> You can also generate the equivalent DDL via a DDL expression
> (`CreateTableExpression` + `storage_options`); see
> [First CRUD application](first_crud.md#2-create-the-table-ddl-expression-vs-raw-sql).

## Key points

1. **IDs are generated client-side**: ClickHouse has no `AUTO_INCREMENT`; on
   `save()` the backend generates an `Int64` via the snowflake algorithm and
   backfills it into the model. See [Client-side snowflake IDs](../capabilities/snowflake_ids.md).
2. **Optional fields → `Nullable(T)`**: an `Optional[int]` on the model maps to a
   `Nullable(Int32)` column. See [Nullable & optional fields](../modeling/nullable.md).
3. **ActiveQuery is read-only (DQL)**: query with `Model.query()`; mutations (DML)
   only go through instance methods (`save()`/`delete()`) or class methods
   (`bulk_insert`/`bulk_delete`).
4. **No transactions**: each `save()` above is independent, with no
   cross-statement transaction guarantee.
5. **Mutations need a table setting**: `UPDATE`/`DELETE` are lightweight
   mutations; the table must be created with `enable_block_number_column`/
   `enable_block_offset_column`.
