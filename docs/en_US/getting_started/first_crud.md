# First CRUD application

This section gives a complete create-table → insert → query → update → delete
flow, more detailed than [Quick start](quick_start.md).

Prerequisites: a running ClickHouse instance (see
[Installation guide](../installation/installation.md#start-a-local-clickhouse-optional-for-testing)),
and the core library + this backend installed.

> 📐 **Design philosophy**: `ActiveQuery` is a read-only query (analogous to DQL)
> and has **no** `delete()`/`update()` methods. Mutations (DML) only go through
> ActiveRecord instance methods (`instance.save()`/`instance.delete()`) or class
> methods (`Model.bulk_delete([...])`).

## 1. Define the model and configuration

```python
from datetime import datetime
from typing import Optional, ClassVar
from pydantic import Field
from rhosocial.activerecord.model import ActiveRecord
from rhosocial.activerecord.base.field_proxy import FieldProxy
from rhosocial.activerecord.backend.impl.clickhouse import ClickHouseBackend
from rhosocial.activerecord.backend.impl.clickhouse.config import ClickHouseConnectionConfig

class User(ActiveRecord):
    __table_name__ = "users"
    __primary_key__ = "id"
    c: ClassVar[FieldProxy] = FieldProxy()

    id: Optional[int] = None
    username: str = Field(min_length=3, max_length=50)
    email: str
    age: Optional[int] = None
    created_at: Optional[datetime] = None

config = ClickHouseConnectionConfig(
    host="localhost", port=8123,
    database="test_db", username="root", password="password",
)
User.configure(config, ClickHouseBackend)
```

## 2. Create the table (DDL expression vs raw SQL)

ClickHouse does not auto-create tables. This backend **inherits and extends** the
core library's DDL expressions: `CreateTableExpression` can generate complete
native ClickHouse DDL. The two approaches are equivalent:

### Approach A: DDL expression (recommended, type-safe, serializable)

```python
from rhosocial.activerecord.backend.expression.statements import (
    CreateTableExpression, ColumnDefinition, DropTableExpression,
)
from rhosocial.activerecord.backend.impl.clickhouse.expression import (
    ClickHouseInt64Type, ClickHouseStringType, ClickHouseInt32Type,
    ClickHouseNullableType, ClickHouseDateTime64Type,
)

# Declare ENGINE / ORDER BY / PARTITION BY / TTL / SETTINGS via storage_options
expr = CreateTableExpression(
    dialect=User.__dialect__,
    table="users",
    columns=[
        ColumnDefinition(name="id", data_type=ClickHouseInt64Type()),
        ColumnDefinition(name="username", data_type=ClickHouseStringType()),
        ColumnDefinition(name="age", data_type=ClickHouseNullableType(ClickHouseInt32Type())),
        ColumnDefinition(name="created_at", data_type=ClickHouseDateTime64Type(6)),
    ],
    storage_options={
        "ENGINE": "MergeTree",
        "ORDER BY": ["id", "username"],
        # see the UPDATE/DELETE prerequisite below
        "SETTINGS": "enable_block_number_column = 1, enable_block_offset_column = 1",
    },
    if_not_exists=True,
)
sql, _ = expr.to_sql()
User.__backend__.execute(sql)   # run the CREATE TABLE
```

`storage_options` accepts the keys below (case/underscore-insensitive; values
are inserted verbatim): `ENGINE`, `ORDER BY`, `PARTITION BY`, `PRIMARY KEY`,
`SAMPLE BY`, `TTL`, `SETTINGS`.

### Approach B: raw SQL (equivalent, for comparison)

```sql
CREATE TABLE IF NOT EXISTS users (
    id         Int64,
    username   String,
    age        Nullable(Int32),
    created_at DateTime64(6, 'UTC')
) ENGINE = MergeTree
ORDER BY (id, username)
SETTINGS enable_block_number_column = 1, enable_block_offset_column = 1;
```

Both produce **exactly the same** DDL, proving this backend has full SQL semantic
coverage — every ClickHouse DDL clause can be generated via expressions, with no
need to hand-write SQL.

### ⚠️ UPDATE/DELETE prerequisite

ClickHouse 26.x **rejects** lightweight UPDATE/DELETE by default (`Code: 48
NOT_IMPLEMENTED`). To enable this backend's `save()` (UPDATE path) and `delete()`,
the table **must** be created with:

```
SETTINGS enable_block_number_column = 1, enable_block_offset_column = 1
```

Or after creation:
`ALTER TABLE users MODIFY SETTING enable_block_number_column = 1, enable_block_offset_column = 1`.
See [Mutations (UPDATE/DELETE)](../capabilities/mutations.md).

## 3. Create (insert)

```python
alice = User(username="alice", email="alice@example.com", age=28)
alice.save()
print(alice.id)            # client-generated snowflake Int64, backfilled after save()

bob = User(username="bob", email="bob@example.com")
bob.save()
```

`save()` issues an INSERT; the primary key is generated by the
[client-side snowflake ID](../capabilities/snowflake_ids.md). Use
`Model.bulk_insert([...])` for batch inserts; the backend generates a contiguous
ID sequence in one shot.

> Note: ClickHouse does not report inserted row counts, so INSERT's
> `affected_rows` is always `0` (unlike UPDATE/DELETE).

## 4. Read (query)

`ActiveQuery` is read-only (DQL), supporting filter/order/pagination/aggregate:

```python
# single row by primary key
u = User.query().where(User.c.id == alice.id).one()

# filter + order + paginate
young = (User.query()
         .where(User.c.age < 30)
         .order_by(User.c.username)
         .limit(20)
         .offset(0)
         .all())

# aggregate
total = User.query().count()
```

## 5. Update (instance mutation)

```python
alice.age = 31
alice.save()      # UPDATE users SET age=31 WHERE id=?  (lightweight update, sync)
```

The mutation executes as a synchronous lightweight UPDATE. `affected_rows` is the
pre-counted number of matched rows. See [Mutations](../capabilities/mutations.md).

> ⚠️ Sorting-key columns (`id`/`username`) **cannot be updated**; doing so raises.

## 6. Delete (single + bulk)

```python
# single instance
alice.delete()

# bulk: query for instances first, then the class method bulk_delete
to_delete = User.query().where(User.c.age < 18).all()
User.bulk_delete(to_delete)
```

> ActiveQuery has no `delete()` method (DQL is read-only). Bulk delete goes through
> the `Model.bulk_delete([...])` class method; per-instance `delete()` is for single rows.

## 7. Transactions: none

```python
with User.transaction():
    bob.save()
    alice.delete()
# if either step fails, the other is NOT rolled back
```

`transaction()` is a no-op context manager that only lets generic code paths run;
there is **no** cross-statement transaction guarantee. See
[Capability boundaries](../introduction/capability_boundaries.md).

## 8. Unsupported operations fail fast

```python
from rhosocial.activerecord.backend.dialect.exceptions import UnsupportedFeatureError

# UPSERT is unsupported
try:
    # ...take the upsert path...
    pass
except UnsupportedFeatureError:
    # fall back to INSERT + ReplacingMergeTree
    ...
```

Probe capabilities with `dialect.supports_*()` before calling, for clearer
cross-backend switching.
