# Mutations (UPDATE/DELETE)

ClickHouse's UPDATE/DELETE differs from OLTP. This backend generates ClickHouse's **lightweight updates/deletes** — `UPDATE ... WHERE` / `DELETE ... WHERE` syntax, rather than the traditional `ALTER TABLE ... UPDATE` asynchronous mutation.

## Generated SQL

The SQL generated by this backend on the UPDATE/DELETE path looks like:

```sql
UPDATE `users` SET `age` = ? WHERE `id` = ?
DELETE FROM `users` WHERE `id` = ?
```

The backend attaches the `mutations_sync=1` session setting at execution time for compatibility with traditional mutation semantics, but the lightweight update itself is synchronous.

## ⚠️ Prerequisite settings: rejected by default

ClickHouse 26.x **rejects** lightweight UPDATE/DELETE by default; executing directly will report:

```
Code: 48. DB::Exception: Lightweight updates are not supported.
Lightweight updates are supported only for tables with materialized
_block_number column. Run 'MODIFY SETTING enable_block_number_column = 1'
command to enable it. (NOT_IMPLEMENTED)
```

To enable this backend's `save()` (UPDATE) and `delete()`, you **must** add the following at table creation:

```sql
CREATE TABLE users (...) ENGINE = MergeTree ORDER BY (...)
SETTINGS enable_block_number_column = 1, enable_block_offset_column = 1;
```

Or add them after table creation:

```sql
ALTER TABLE users MODIFY SETTING
  enable_block_number_column = 1,
  enable_block_offset_column = 1;
```

## affected_rows semantics

| Operation | `affected_rows` |
|------|----------------|
| INSERT | `0` (ClickHouse does not report the number of inserted rows; the actual count requires a separate `count()`) |
| UPDATE | pre-counted number of rows matching the WHERE clause |
| DELETE | pre-counted number of rows matching the WHERE clause |

```python
alice.age = 31
r = alice.save()           # UPDATE，affected_rows = 1（匹配行）
bulk = User.bulk_delete(to_delete)   # affected_rows = 匹配行预计数
```

ClickHouse cannot accurately report "how many rows were actually changed" during lightweight execution; it can only report the WHERE match count. For an exact count, query `count()` before and after the mutation and compare.

## Single vs batch mutations

```python
# 单个：实例方法
alice.save()         # UPDATE
alice.delete()       # DELETE

# 批量：类方法（先查询得实例列表）
to_delete = User.query().where(User.c.age < 18).all()
User.bulk_delete(to_delete)

to_upsert = [User(...) for ...]
User.bulk_insert(to_upsert)
```

> `ActiveQuery` is read-only (DQL) and **has no** `delete()`/`update()`. Batch mutations go through the `Model.bulk_insert`/`bulk_delete` class methods.

## Cost of mutations and alternatives

| Operation | Cost | Alternative |
|------|------|------|
| UPDATE few rows | rewrites affected parts | `ReplacingMergeTree` write a new version, dedup at merge |
| DELETE few rows | soft delete, wait for merge | `CollapsingMergeTree` + sign marking |
| Bulk DELETE | drop by partition | `ALTER TABLE ... DROP PARTITION` |

## Sorting key columns cannot be updated

`ORDER BY` columns (i.e., the primary key sorting key) **cannot** be modified by UPDATE — it raises an error. To change a primary key column, you can only delete the old row and insert a new one (or rebuild the table).

## No transactions

Each UPDATE/DELETE executes independently, with no cross-statement transactions. `transaction()` is a no-op context manager; rollback does not undo completed mutations. See [Capability boundaries](../introduction/capability_boundaries.md).
