A [ClickHouse](https://clickhouse.com/) backend for
[rhosocial-activerecord](https://github.com/rhosocial/python-activerecord) —
the ActiveRecord pattern adapted to a columnar, OLAP engine.

> **This package is not on PyPI yet.** The PyPI badge above is aspirational;
> install from source until the first release is published.

## Quick Start

```python
from typing import ClassVar, Optional

from pydantic import Field

from rhosocial.activerecord.base import FieldProxy
from rhosocial.activerecord.backend.impl.clickhouse.backend import ClickHouseBackend
from rhosocial.activerecord.backend.impl.clickhouse.config import ClickHouseConnectionConfig
from rhosocial.activerecord.backend.expression import CreateTableExpression
from rhosocial.activerecord.backend.expression.statements import ColumnDefinition
from rhosocial.activerecord.backend.expression.types import IntegerType, VarCharType
from rhosocial.activerecord.model import ActiveRecord


class User(ActiveRecord):
    __table_name__ = "users"

    id: Optional[int] = None          # snowflake id, assigned client-side
    username: str = Field(min_length=3, max_length=50)
    email: str
    age: Optional[int] = None         # needs a Nullable(Int32) column

    c: ClassVar[FieldProxy] = FieldProxy()


User.configure(
    ClickHouseConnectionConfig(
        host="localhost",
        port=8123,
        database="test_db",
        username="default",
        password="",
    ),
    ClickHouseBackend,
)

dialect = User.__backend__.dialect
User.__backend__.execute(*CreateTableExpression(
    dialect,
    "users",
    columns=[
        ColumnDefinition(dialect, "id", IntegerType(dialect)),
        ColumnDefinition(dialect, "username", VarCharType(dialect, 50)),
        ColumnDefinition(dialect, "email", VarCharType(dialect, 255)),
    ],
).to_sql())
# CREATE TABLE `users` (`id` Int32, `username` String, `email` String)
```

> **Schema note.** ClickHouse is not a row store. The generated DDL above is
> only a starting point: a MergeTree table needs `ENGINE` / `ORDER BY`, and
> optional model fields require `Nullable(T)` columns — writing NULL into a
> non-nullable `String` column stores an empty string instead. Primary keys
> map to the `ORDER BY` sorting key, which cannot be updated.

```python
user = User(username="alice", email="alice@example.com")
user.save()          # id is generated client-side and returned

rows = User.query().where(User.c.age < 30).order_by(User.c.username).all()

user.age = 31
user.save()          # lightweight mutation, synchronous completion
user.delete()
```

### No async backend

`clickhouse-connect` is a synchronous-only library, so this backend is
synchronous only. `AsyncClickHouseBackend` exists as an **import placeholder**
so that testsuite providers and CLI helpers keep loading, but it raises
`NotImplementedError` on instantiation. This is deliberate: there is no
half-working async layer.

```python
from rhosocial.activerecord.backend.impl.clickhouse.backend import AsyncClickHouseBackend

AsyncClickHouseBackend()   # NotImplementedError
```

## What This Backend Does NOT Do

Relational guarantees ClickHouse does not provide are **declared through
capability switches and fail fast** with `UnsupportedFeatureError` rather
than being silently emulated.

| Feature | Behaviour |
|---|---|
| ACID transactions | `transaction()` degrades to a no-op context manager; rollback semantics raise |
| AUTO_INCREMENT | No such thing. Client-side snowflake `Int64` ids generated by the backend |
| FOREIGN KEY / UNIQUE | Not emitted; DDL stays ClickHouse-native (`ENGINE`, `ORDER BY`, skip indexes) |
| UPSERT / ON CONFLICT / REPLACE | Raises `UnsupportedFeatureError` |
| JSON access | Native functions: `JSONExtractString` / `JSONExtractRaw` / `JSON_VALUE` |
| UPDATE / DELETE | Lightweight mutations run with `mutations_sync=1`; `affected_rows` is a pre-count of matched rows |
| FOR UPDATE row locking | Unsupported |
| Uniqueness | Your engine's job — `ReplacingMergeTree`, `CollapsingMergeTree` |
| Async | Not available; see above |

131 of the switches this backend defines stay `False` at every probed
version. Beyond the ones in the table, that includes: `check_constraint`,
`create_sequence`, `drop_sequence`, `auto_increment`, `clone`, `call`,
`binlog`, `analyze_table`, `check_table`, `checksum_table`, `descending_index`,
`add_constraint`, `drop_constraint`, `add_partition`, `attach_partition`,
`detach_partition`, `deferrable_*`, and every MySQL spatial `ST_*` surface
plus the MySQL 9.0 `VECTOR` type.

## Version Gates

Only one gate is enforced:

| Min version | Capabilities that turn on |
|---|---|
| 26.3 | `json_merge_patch` |

The backend otherwise assumes a recent server and does not compare versions
per capability.

## Testing

A local ClickHouse is required. The shared testsuite is bridged under
`tests/rhosocial/activerecord_clickhouse_test/feature/`:

```bash
export PYTHONPATH=src:tests
.venv3.14-ubuntu26.04/bin/pytest tests/rhosocial/activerecord_clickhouse_test \
  -p no:logging -p no:cacheprovider
```

Connection defaults live in `tests/config/clickhouse_scenarios.yaml`; override
the path with `CLICKHOUSE_SCENARIOS_CONFIG_PATH`. CI exercises Python
3.10–3.14 against ClickHouse 25.8, 26.3 and 26.7.
